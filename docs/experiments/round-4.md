# 라운드 4: 검색 단계에서 생성 모델을 쓰는 후보

검색 단계를 다시 열어, 생성 모델이 넘길 문서를 고르는 후보와 검색어를 넓히는 후보 넷을 dev 250문항으로 견주고 리트리버를 고정한다. 규칙은 `docs/optimization.md`를 따른다. 후보가 겨냥한 문제와 그 근거는 `docs/experiments/round-2.md`의 "겨냥한 문제가 풀렸는가"와 `docs/experiments/round-3.md`의 "남은 문제와 다음 단계 제안"에 있다.

- 실행: `configs/exp/r4-select.yaml`(커밋 `3ede727`), `r4-expand.yaml`(`643425c`), `r4-expand-select.yaml`(`8a992fb`), `r4-expand-select-chunks.yaml`(`1cbafe7`). 넷 다 검색을 돌렸고, 뒤의 둘은 생성·채점까지 돌렸다.
- 검색의 기준은 `r1-hybrid-rerank`다. 검색 지표는 근거 문서가 있는 235문항으로 잰다.
- 답의 기준은 `r3-complete`다. 검색이 `r1-hybrid-rerank`이고 생성 조건이 두 후보와 같다(`prompts/answer-complete.txt`, 답의 토큰 한도 1024). 답 지표는 `info_not_found`를 뺀 240문항으로 잰다.
- 라운드를 시작할 때 정한 것: 후보 4개, 주 지표 Recall@5, 넘기는 청크 5개, 답 점수는 뒤의 두 후보로 잰다.

- `r4-select`, `r4-expand-select`, `r4-expand-select-chunks`는 구간이 0을 넘는다. `r4-expand`는 기준과 동률이다.

- `r0-naive` 대비 누적 차이는 `r4-select` +0.283 [+0.222, +0.345], `r4-expand` +0.239 [+0.180, +0.301], `r4-expand-select` +0.357 [+0.299, +0.419], `r4-expand-select-chunks` +0.359 [+0.298, +0.422]다.

## 겨냥한 문제가 풀렸는가

### 후보에 있으나 리랭커가 5위 밖에 둔다: 생성 모델이 고르면 풀린다

- `r4-select`는 기준과 같은 후보에서 고르는 단계만 바꿨다. Recall@5가 +0.045 [+0.016, +0.076]이고, 오른 문항이 24개, 내린 문항이 5개다.
- 첫 자리에 근거 문서를 두는 문항도 늘었다. Recall@1이 0.544에서 0.640이 됐다(+0.096 [+0.055, +0.140]).
- 리랭커는 질문과 청크 한 쌍씩을 따로 매긴다. 생성 모델은 20문서를 한꺼번에 읽고 견주어 고른다.

### 근거 문서가 후보에 없다: 넓히기만으로는 풀리지 않고, 고르기와 합치면 풀린다

- `r4-expand`는 기준과 동률이다(+0.000 [−0.032, +0.032], 오른 문항 10개, 내린 문항 10개). 라운드 2에서 후보 수를 늘렸을 때와 같다. 후보가 넓어져도 리랭커가 근거 문서를 5위 안에 올리지 못한다.
- 같은 넓힌 후보에서 생성 모델이 고르면 달라진다. `r4-expand-select`는 `r4-expand`보다 +0.119 [+0.081, +0.159](오른 문항 40개, 내린 문항 2개), `r4-select`보다 +0.074 [+0.041, +0.110](23개, 1개)다.
- 가장 크게 오른 유형은 손실이 가장 컸던 semantic(0.532에서 0.710)과 project_related(0.417에서 0.597)다. 질문과 다른 말로 쓰인 문서, 여러 문서에 흩어진 근거를 겨냥한 후보였다.

## 알아 둘 것

- 후보의 설계값(검색어와 가상의 글의 수, 검색마다 가져오는 후보 수, 생성 모델에 보여 주는 문서 수, 순위를 섞는 가중치, 고르는 프롬프트)은 라운드를 시작하기 전에 dev 문항으로 맞춘 값이다. 그래서 이 보고서의 dev 수치는 낙관적이다. 최종 구성이 기준선보다 나은지는 test로 확인한다.
- 생성 모델은 temperature 0에서도 실행마다 출력이 다르다. `r4-expand-select`와 `r4-expand-select-chunks`는 `expand`의 설정이 같은데, 250문항 가운데 만든 검색어 8개가 모두 같은 문항이 131개, 가상의 글 4개가 모두 같은 문항이 32개였다. 그 결과 고르는 문서도 달라져, 한쪽이 넘긴 문서가 다른 쪽이 넘긴 문서 안에 모두 드는 문항은 150개다. 계획에서는 두 후보가 고르는 문서가 같다고 보았으나 그렇지 않았다.
- 그래서 두 후보의 차이에는 문맥 구성의 효과와 다시 돌렸을 때의 흔들림이 섞여 있다. 문항별 부트스트랩 구간은 문항을 다시 뽑았을 때의 흔들림만 담고, 다시 돌렸을 때의 흔들림은 담지 않는다. 같은 구성을 여러 번 돌려 이 흔들림의 크기를 재지는 않았다.
- `r4-expand-select-chunks`의 검색은 머지 전에 단위 브랜치의 커밋(`1cbafe7`)에서 돌렸다. 실행 폴더의 `run.json`에 적힌 커밋은 squash 머지 뒤 main에 남지 않는다. 코드와 config는 머지된 것(`8a6e772`)과 같다.
- 기준의 검색 시간 153초는 이 라운드에서 `r1-hybrid-rerank`를 다시 돌려 잰 값이다(`20261124-024124`). 다시 돌린 실행은 250문항 중 249문항의 결과가 원래 실행(`20261122-103232`)과 같고, 점수는 235문항 모두 같다. 차이와 구간은 원래 실행으로 냈다.
- `r4-select`의 검색 시간 2,072초는 Qdrant의 벡터 파일이 메모리에 다 올라와 있지 않은 상태에서 잰 값이라 다른 실행과 견줄 수 없다. 그 상태에서는 문서 전체에 대한 정확 검색 한 번이 약 6초였고, 다 올라온 상태에서는 0.35초다. 원래 기준 실행의 256초도 그 상태의 값이다.
- `r4-expand`의 첫 전체 실행은 64분째에 Qdrant의 검색 시간 한도(60초)를 넘겨 끝나지 못했다. 생성 서버를 띄울 때 읽은 모델 가중치가 파일 캐시를 차지해 벡터 파일(19.4GB)이 메모리에서 밀려난 것이 원인이었다. 가중치의 캐시를 비우고 다시 돌렸고, 그 뒤의 실행은 모두 벡터가 메모리에 올라온 상태에서 돌렸다. 검색 결과는 이 상태와 무관하다. 서버를 띄운 뒤 캐시를 비우는 일은 지금은 손으로 한다.
- 두 후보의 생성과 채점은 다른 실행과 겹치지 않게 하나씩 돌렸다.
